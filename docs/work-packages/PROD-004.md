# PROD-004 — академические статусы и допустимые переходы

## Идентификация
- **ID:** `PROD-004`
- **Название:** Определить академические статусы, область действия и разрешённые переходы
- **Статус:** [~] In progress
- **Владелец:** MAGNUS project workflow
- **Создано / обновлено:** 2026-11-11

## 1. Цель и ожидаемый результат
Утвердить точную семантику академических состояний MAGNUS, их уровень (профиль человека или отдельная программа), допустимые переходы, инициаторов и подтверждающие роли. Развести зачисление, фактическое начало обучения, академический отпуск, добровольное прекращение, отчисление и завершение программы. Результат — статусная модель и матрица переходов, пригодные для последующей серверной реализации без блокировки других программ студента.

## 2. Контекст и текущее состояние
- PROD-001…PROD-003 завершены; базовый путь описан в `docs/STUDENT_LIFECYCLE.md`.
- Рабочая ветка `magnus-source-upload`; исходный HEAD `0a7187a5850c5ce66a118fe3f561ba3dacba19e2`; полный CI [43002935812](https://github.com/Gennzy/magnus-mini-app/actions/runs/43002935812) — SUCCESS.
- `studentData.js` читает один `payload.academicStatus`: applicant/active/academic_leave/expelled/graduated. При отсутствии значения выводит active по наличию зачислений, иначе applicant.
- `enrollProgram` сохраняет только дату в `payload.enrollments[programId]`; у конкретного зачисления нет собственного статуса.
- `admin.js:updateAcademicStatus` меняет один статус на весь профиль. Есть отдельные проверки для active и graduated, но нет полной матрицы переходов.
- `academicAccessError` блокирует часть действий по глобальному статусу; отдельные действия проверяют доступ неодинаково.
- Один пользователь может одновременно обучаться по нескольким программам, а подписка хранится отдельно.

## 3. Границы

### IN — входит
- Разделить профиль, возможную заявку, зачисление на конкретную программу, статус её обучения и подписочный доступ.
- Определить значения «абитуриент», «зачислен», «активно обучается», «академический отпуск», «добровольно прекратил», «отчислен», «программа завершена».
- Определить уровень статусов, переходы, роли, основания и историю.
- Описать сводное положение профиля при нескольких программах.
- Описать безопасное сопоставление старых глобальных статусов с новой моделью.
- Добавить модель в обязательные проектные документы и документационные тесты.

### OUT — не входит
- Новые поля, миграции, API, backend-переходы, RBAC и изменение записей студентов.
- UI академического паспорта и админ-панели.
- Формальная приёмная кампания, конкурс, документы и ручная комиссия.
- Критерий первого учебного действия — PROD-005.
- Зачёт, пороги, попытки, пересдачи и апелляции — PROD-006/007.
- Подписки, заморозка, продление и возвраты — PROD-008.
- Сертификаты — PROD-009; юридическая проверка — PROD-010.

## 7. План тестирования

### Автоматические
- `npm run check:docs` — обязательный документ и согласованность активного WP.
- `npm run test:docs` — позитивные и негативные случаи, включая отсутствующую модель.
- Полный `MAGNUS visual smoke tests`: tutor coverage, payment invariants, backend syntax, build, desktop/mobile Playwright smoke.

### Ручные
- Source review `studentData.js`, `admin.js`, `schema.js`, `main.js`, `STUDENT_LIFECYCLE.md`, `LEARNING_MODEL.md`, ADR-0003/0004.
- Проверить случаи одного студента с двумя и более программами.
- Убедиться, что профильный статус не подменяет статусы программ, а подписка не меняет академическое положение.
- Telegram-проверка не нужна: runtime не меняется.

### Негативные и граничные
- Нельзя называть «заявку поданной» без отдельного процесса подачи.
- Нельзя считать зачисление фактической активностью до определения события PROD-005.
- Нельзя вручную выставлять «завершено» без серверного выполнения требований.
- Отпуск по одной программе не блокирует вторую активную программу.
- Отчисление по одной программе не становится запретом на весь MAGNUS.
- История переходов не удаляется и не перезаписывается.
- Неоднозначный старый глобальный статус не переносится вслепую на все программы.
