> **Этот документ — единый источник правды по разработке MAGNUS.** Перед любой новой задачей, включая продолжение в новом чате, сначала читаем этот файл и `docs/PROJECT_STATE.md`. Устные планы и сообщения в чате не заменяют обновление этих документов.

- Проект: MAGNUS University — цифровая образовательная платформа с учебными программами, сопровождением, оцениванием и административной системой.
- Рабочая ветка: `magnus-source-upload`. Ветка `main` не используется для этой серии работ.
- Mini App: https://app9020486965.tgcloud.ai/
- Карта создана: 11 ноября 2026 года.
- Последнее зафиксированное состояние: см. `docs/PROJECT_STATE.md`.

## 1. Жёсткие правила разработки

Эти правила важнее желания «добавить ещё одну полезную вещь».

### 1.1. Правило одной активной задачи

1. В каждый момент времени существует **одна активная задача** (Work Package, WP).
2. Не начинаем следующую задачу, пока текущая не прошла все критерии завершения и не получила статус DONE в этой карте.
3. Новые идеи, найденные баги вне текущей задачи и улучшения записываются в соответствующий раздел BACKLOG. Они не переключают текущую работу.
4. Если обнаружен блокирующий дефект, который мешает текущей задаче, исправляем его в рамках текущего WP. Не начинаем параллельную функцию.
5. Если контекст чата заканчивается, работа не «переосмысляется»: в новом чате читаются эта карта и состояние проекта, восстанавливается текущий WP, и работа продолжается с его незакрытого пункта.
6. Нельзя объявлять задачу готовой только потому, что файлы закоммичены или Workflow запущен.

### 1.2. Единый формат Work Package

Каждый WP до начала реализации оформляется по шаблону `docs/WP_TEMPLATE.md`. Запись должна содержать: ID и название, статус, цель и ожидаемый результат, контекст/проблему, границы IN/OUT, зависимости и блокеры, точный список файлов/областей, критерии приёмки с проверяемыми результатами, тесты (автоматические и ручные), план публикации/проверки после публикации и условия закрытия. Не начинать кодирование, пока обязательные поля не заполнены. Если раздел неприменим, явно указать «Не требуется» и причину.

### 1.3. Обязательный цикл каждого WP

Для каждой задачи выполняются шаги в указанном порядке:

1. **Восстановление контекста:** прочитать MASTER_ROADMAP и PROJECT_STATE, сверить актуальную ветку/HEAD и последние Actions.
2. **Фиксация границ:** записать цель, точные файлы/области, что не входит в задачу и критерии приёмки.
3. **Осмотр текущей реализации:** изучить затрагиваемые экраны, API, данные, права, миграции и тесты. Не переписывать рабочее без необходимости.
4. **Реализация:** сделать только текущую задачу. Не добавлять несвязанные функции «заодно».
5. **Проверка кода:** синтаксис, сборка, контракты API, миграции, сохранение данных, регрессии.
6. **Проверка интерфейса:** desktop и mobile, состояния loading/empty/error/success, длинные тексты, Telegram WebView, доступность элементов.
7. **Проверка сценария:** пройти пользовательский путь от начала до конца. Smoke test не заменяет проверку логики сервера.
8. **Публикация:** дождаться завершения актуального Deploy workflow для последнего SHA.
9. **Проверка после публикации:** подтвердить результат по доступным runtime-проверкам; если реальная проверка требует пользователя/Telegram-аккаунта, явно отметить её как ручную и не выдавать за выполненную.
10. **Закрытие:** обновить чек-листы, статус WP, HEAD, ссылки на Actions, известные ограничения и следующий WP в PROJECT_STATE.
11. Только после этого WP считается **DONE**, и можно переходить к следующему.

### 1.4. Что означает статус

- `[x]` — реализовано и критерии приёмки проверены.
- `[~]` — частично реализовано, есть незакрытая часть или не пройдена полная проверка.
- `[?]` — код/интерфейс есть, но поведение требует отдельной проверки.
- `[ ]` — не начинали.
- `[!] ` — блокер; переход дальше запрещён, пока он не снят.

Не повышать статус до `[x]` по предположению. Для внешнего сервиса, платежа, Telegram или базы данных наличие кода не означает, что интеграция проверена.

### 1.5. Техническая дисциплина

- Не коммитить секреты, токены, ключи, локальные конфиги и персональные данные. Не менять `.tgcloud` credentials.
- Не ломать текущие ID курсов и уроков, Telegram-профили, существующие зачисления, прогресс, экзамены и сертификаты.
- Любую миграцию проектировать с обратной совместимостью; не удалять старые данные без отдельного плана.
- Сначала серверная проверка прав и бизнес-правил, затем UI. Клиент не является источником истины для оценок, завершения, оплат и статусов.
- Единый каталог учебных программ должен быть источником правды. Не размножать массивы ID уроков и названия программ по разным файлам.
- Не имитировать преподавателей, аккредитацию, дипломы, оценки, платежи, расписание или работающие интеграции.
- Все новые пользовательские тексты — на русском, без канцелярита и без «ИИ-слопа». ИИ не выдавать за человека.
- Сову MAGNUS сохранять как часть фирменной идентичности. Не заменять её случайной буквой, эмодзи или упрощённой иконкой.
- Перед изменениями смотреть текущий дизайн и существующие компоненты. Не устраивать полный редизайн вместо точечной задачи.
- После каждого WP — отдельная запись в состоянии проекта. Не оставлять незавершённые изменения без отметки.

## 2. Определение «университет готов»

MAGNUS можно считать готовым к полноценному публичному запуску только когда одновременно выполнено следующее:

- Студент может зарегистрироваться/идентифицироваться, выбрать факультет и программу, поступить и понимать свой статус.
- Каталог, образовательные программы, семестры/модули, дисциплины, уроки и требования связаны единой моделью данных.
- Студент может пройти полный путь: изучение → практика → обратная связь → контроль → экзамен → итог программы → документ о завершении.
- Все результаты хранятся на сервере, имеют историю, правила пересдачи и понятные причины отказа.
- AI-наставник знает программу и контекст конкретного урока, не выдумывает факты и корректно сообщает о неопределённости.
- Администрация может управлять студентами, программами, контентом, оцениванием, обращениями, платежами и аудитом без ручного редактирования БД.
- Поддерживаются необходимые роли сотрудников, разделение полномочий и журнал критических действий.
- Работают поддержка, уведомления, расписание (если оно заявлено), подписки/оплата (если они включены в бизнес-модель).
- Есть мониторинг, резервное копирование/восстановление в пределах возможностей платформы, проверка безопасности и регрессионные тесты.
- Мобильный Telegram Mini App и desktop одинаково пригодны для реального ежедневного обучения.
- Публичные обещания соответствуют фактическому статусу платформы. Сертификат MAGNUS не называется государственным дипломом или аккредитованной квалификацией без соответствующих законных оснований и подтверждений.

# 6. Формат обновления карты после каждой задачи

После каждого завершённого WP обновить:

1. Статус соответствующих ID в этой карте.
2. `docs/PROJECT_STATE.md`: новый HEAD, активный WP, что изменено, что проверено, ссылки на актуальные Actions, ручные проверки и известные ограничения.
3. Текущий WP: только один.
4. Backlog: добавлять новые находки без переключения приоритета.

Шаблон завершения WP:

```text
WP:
Результат:
Изменённые файлы:
Изменения данных/миграции:
Автоматические проверки:
Ручные проверки:
Deploy SHA и статус:
Visual QA SHA и статус:
Остаточные ограничения:
Статус в MASTER_ROADMAP:
Следующий WP:
```

## 7. Инструкция для нового чата

При продолжении MAGNUS не предлагать новую функцию и не придумывать новый план по последнему сообщению. Сначала:

1. Открыть `docs/MASTER_ROADMAP.md`.
2. Открыть `docs/PROJECT_STATE.md`.
3. Проверить последний commit рабочей ветки и Actions.
4. Найти единственный активный WP и незакрытый критерий.
5. Продолжить именно его. Если он уже полностью завершён — сначала корректно закрыть его в документах, затем взять следующий WP из очереди.

**Главное правило: не распыляться. Один WP — от определения задачи до проверенного релиза и обновлённой документации.**
